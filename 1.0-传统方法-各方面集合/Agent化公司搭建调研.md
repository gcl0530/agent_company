# Agent 化软件公司搭建调研

> 调研日期：2026-07-22。本文记录公开可追溯资料，不把厂商叙述等同于已被独立审计的经营事实。

## 结论

目前公开可验证的成熟形态不是“没有人的全自动公司”，而是**人类主导、Agent 扩展执行带宽的混合组织**。最可复用的实践集中在四点：

1. 围绕结果临时组队，而不是把 Agent 固定成一个虚拟部门。
2. 将稳定、低风险、高频的工作先做成有质量门的工作流；开放性工作才使用自主 Agent。
3. Agent 必须有可观察的工具调用、输入输出、停机条件、评估和人工升级点。
4. 工具链按业务部门真实的摩擦和结果需求建设，不能为了“多 Agent”而建设平台。

因此，本仓库采用“部门能力系统 + 项目事实包 + 工具服务 + 机制进化”的结构，而不宣称构建无人值守公司。

## 公开实践与可借鉴点

| 来源 | 可确认的公开信息 | 可借鉴点 | 不应直接照搬的部分 |
| --- | --- | --- | --- |
| [Microsoft Work Trend Index 2025](https://www.microsoft.com/en-us/worklab/work-trend-index/2025-the-year-the-frontier-firm-is-born) | 提出人类与 Agent 的混合团队、按目标动态组队的 Work Chart、人机配比和 Agent 管理能力。报告也列举了 AI-first 小团队的案例。 | 部门保留责任边界，项目按目标组合角色；需要管理人机配比与 Agent 负责人。 | 该报告是趋势研究，不是针对软件外包公司的可直接执行 SOP。 |
| [Anthropic: Building Effective AI Agents](https://www.anthropic.com/research/building-effective-agents) | 区分预定义工作流和自主 Agent；推荐从最简单方案开始，按任务增加复杂度；强调工具接口、环境反馈、停止条件、沙箱和人工检查点。 | 把部门工作先拆成可验证工作流和工具服务，再逐步提高 Agent 自主性。 | 文章描述工程模式，不提供公司组织架构或商业责任模型。 |
| [Factory](https://www.factory.ai/) | 将 Agent 能力覆盖软件生命周期，并强调持续信号、部署和自我改进。 | 工具链应连接需求、代码、测试、部署和反馈，而不是只做代码生成。 | 厂商产品能力不等于本公司已具备的交付能力。 |
| [Cognition / Devin](https://www.cognition.ai/) | 将软件 Agent 放入既有代码库和团队工具中，承担计划、编写、测试和交付等工程动作。 | 工程 Agent 应工作在真实代码、测试和协作环境中，产物可被工程团队审查。 | 自主工程能力仍不替代架构取舍、发布批准和客户责任。 |
| [Palantir AIP](https://www.palantir.com/platforms/aip/) | 公开强调 AI 提议动作、人员查看底层逻辑和执行历史、人员批准高影响动作。 | 把权限、审计、动作记录和人工批准视为工具服务的一部分。 | 平台能力和投入规模不适合作为小型公司的直接实现目标。 |

## 对本公司的设计影响

| 观察 | 本仓库采用的落点 |
| --- | --- |
| Agent 团队按目标组合 | `1.1-项目事实与交付档案/` 中每个项目按需选择前端、后端、算法、交付与 Agent 工作单元。 |
| 先工作流后自主 Agent | `0.5-Agent-工具链与Agent平台/` 先提供项目创建、完整性检查、链接检查等确定性服务。 |
| 人机责任必须可见 | `AGENTS.md` 与项目计划要求目标、输入、输出、质量门、权限、升级和沉淀。 |
| 执行必须能复盘 | `0.6-Agent-迭代式E进化/` 记录运行节奏、指标、试验、升级与回退。 |
| 平台从业务需求生长 | 工具服务先由部门提交请求、定义受益指标，再进入试用和标准化。 |

## 采纳边界

- 任何外部案例只能作为方法输入，不作为客户承诺、产能估算或安全结论。
- 对外沟通、报价、合同、生产发布、部署和验收仍由人类负责人批准。
- 新 Agent 或自动化先在单一、可回滚任务中试用；累计足够证据后才能成为公司标准服务。
