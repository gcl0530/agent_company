# 机制运行与进化闭环

## 目标

让公司机制服务真实软件交付：发现摩擦，提出可验证改进，在有限范围试用，用结果决定标准化、修改或回退。机制不是为增加会议、文档或 Agent 数量而存在。

## 三层运行节奏

| 节奏 | 参与者 | 固定输入 | 必须输出 | 决策权限 |
| --- | --- | --- | --- | --- |
| 项目周节奏 | 产品、项目、技术、交付 owner | 目标、进展、风险、测试/现场事实 | 本周结论、阻塞、下周承诺、升级项 | 项目负责人；范围/风险升级给业务负责人。 |
| 双周能力节奏 | 各部门 owner、工具链 owner | 重复摩擦、质量问题、Agent/工具使用证据 | 服务请求、改进试验、能力缺口 | 部门负责人决定试用；跨部门投入升级。 |
| 月度经营与机制节奏 | 业务负责人、部门负责人 | 项目结果、交付质量、成本、客户反馈、试验结果 | 优先级、资源调整、机制升级/下线 | 人类业务负责人。 |

项目结束后必须进行复盘；出现重大交付、安全或客户风险时，不等待固定节奏，立即升级。

## 机制进化流程

`观察事实 -> 定义问题 -> 提出假设 -> 小范围试验 -> 度量结果 -> 标准化/修改/回退 -> 写回事实源`

### 1. 观察事实

来源可以是项目问题、客户反馈、测试失败、重复手工劳动、Agent 运行记录或工具成本。记录现象、影响、证据位置和责任人，不直接把抱怨写成机制结论。

### 2. 试验合同

每项机制或工具试验必须写明：

| 项目 | 必须内容 |
| --- | --- |
| 问题与基线 | 当前成本、周期、遗漏、质量或风险证据。 |
| 改进假设 | 预计改善什么，不改善什么。 |
| 试用范围 | 一个项目、一个部门或一个任务类型；不直接全公司推广。 |
| 责任与权限 | 人类 owner、Agent/工具可读写执行范围、升级人。 |
| 指标与阈值 | 成功、失败和停止条件。 |
| 回退 | 停用方式、原流程和数据/工件保留方式。 |

### 3. 决定与沉淀

- **标准化**：达到指标且未增加不可接受风险时，写入对应部门手册、模板或工具服务目录。
- **修改**：有收益但质量、成本、权限或体验存在缺口时，保留试用并创建改进项。
- **回退/下线**：未达到目标、风险不可接受或人工审查成本高于收益时，停止使用，保留证据和教训。

## 最小指标集

| 维度 | 建议指标 | 使用方式 |
| --- | --- | --- |
| 客户与结果 | 验收通过率、反馈关闭周期、返工原因 | 判断是否真正提高交付结果。 |
| 项目流动 | 从确认需求到可验证结果的周期、阻塞时长、计划偏差 | 判断协作和依赖是否改善。 |
| 工程质量 | 缺陷逃逸、回归通过率、部署失败/回退次数 | 判断自动化是否牺牲质量。 |
| Agent/工具效果 | 成功率、人工复核率、节省时间、失败类型、单次成本 | 判断服务是否值得保留。 |
| 组织能力 | 关键职责覆盖率、能力缺口关闭率、可复用资产采用次数 | 判断组织是否在积累。 |

指标用于比较改进前后，不用于脱离项目事实的绩效表演；没有基线时先记录基线，再评价试验。

## 与 S1-S5 的关系

现有讲解页中的 S1-S5 可继续作为软件研发阶段语言。每一阶段都应在项目事实包留下对应证据：产品定义和计划进入 S1/S2，设计实现与验证进入 S3/S4，交付、复盘和机制回写进入 S5。阶段完成以质量门和结果证据为准，不以文档状态为准。

## Agent 能力进化

Agent 能力也按上述试验流程进化。每次准备扩大 Agent 的写入、执行或自动化权限时，先在 `0.5-Agent-工具链与Agent平台/agent_maturity_and_promotion.md` 定义任务范围、证据、停止条件和审批人；复盘后再决定晋级、保持、降级或停用。公司不承诺“最终全自动化”，而是随模型、工具、验证能力和实际风险持续调整人机边界。
